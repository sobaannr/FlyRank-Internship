Abstract

Five sentences, no padding

Question: given a large content inventory and a small review capacity each cycle, which pages should a reviewer look at first? Method: using FlyRank's 79-million-row search warehouse, I built a genuine prior-month-to-future-month decline label (March → April 2026) and compared a Random Forest classifier against a transparent CTR-vs-position-tier baseline rule, evaluated under a client-grouped holdout split so no client's pages appear in both train and test. Result: the baseline rule outperformed the Random Forest at both k=20 and k=50 — and a plain random split (no client grouping) inflated the model's own reported score from a genuine 0.560 to an illusory 0.740 Precision@50, a leakage effect I caught and corrected mid-project. So what: a well-targeted, interpretable rule beat a general-purpose classifier here, and the validation design mattered more to the final number than the choice of model. Output: a ranked, human-reviewed content action queue with reason codes, a documented false-positive pattern, and explicit no-go rules for what should never be automated.

01 — Introduction

The problem isn't finding declining pages. It's ranking them.

Content teams don't lack data — they lack review capacity. A site with tens of thousands of pages might have bandwidth to manually review a few dozen per cycle. The question that matters isn't "which pages are declining?" in the abstract; it's "of everything competing for a reviewer's next hour, what should they open first?"

This report treats that as a ranking problem, builds a baseline and a model to solve it, and — more importantly — treats the process of validating that solution as seriously as the solution itself. The most useful result in this project turned out to be catching my own model's inflated score before it went anywhere near a client.

Decision supported Which pages a content reviewer opens first each cycle, using a ranked queue with reason codes — not an automated publishing or editing tool.
02 — Data

79M rows, one table, two months

This study uses the FlyRank/internship-warehouse release on Hugging Face (build flyrank_pseudonymized_warehouse_release_v20260703), specifically the fact_content_daily_performance fact table — one row per content page per day, fully pseudonymized (hashed client and content IDs; no raw URLs, titles, or queries).

Excluded, and why GA4-derived signals (sessions, engaged sessions) — GA4 coverage was only ~4.2% of rows in the feature month, so including them meant mostly filled zeros standing in for "unknown," which measurably hurt rather than helped the model. Any rebuilt FlyRank product flag (health_score, priority_score, action_type) was excluded on principle: these are the product's own decisions, not observable signals, and using them would let a model simply learn to copy an existing rule rather than find real signal.
03 — Methodology

What went in, and how it was tested

Features — four GSC-only, same-window signals, each knowable before the decision point: impressions, clicks, avg_position, ctr.

Label — is_declining: future-month impressions fall more than 20% versus the feature month. A magnitude threshold, not "any decrease," to avoid flagging ordinary noise.

Baseline — a transparent rule: score = (position-tier-expected CTR − page CTR) × log(1+impressions). Reason code ctr_below_tier_expected. This directly encodes the domain fact that raw CTR is mostly explained by position, so comparisons only make sense within a tier.

Model — Random Forest (200 trees, depth 6, balanced class weight). Chosen because individual signal correlations with the label were all weak (max |0.16|) in earlier exploration — evidence the real pattern lives in feature interactions, which trees capture and a linear rule structurally cannot.

Validation — client-grouped holdout (GroupShuffleSplit on client ID): no client's pages appear in both train and test. This single design choice turned out to be the most consequential decision in the whole project (see Results).

Leakage checks — no product flags used anywhere; feature month never overlaps label month; ctr is derived only from feature-month data; client grouping closes the row-independence gap that a plain random split leaves open.

04 — Results

The number that changed when I stopped cheating

Before comparing model to baseline, here's the finding that shaped everything else in this report: the same model, same features, same label — scored very differently depending on how the test set was built.

Precision@50 — same model, same data
0.740
A plain 80/20 split lets pages from the same client land in both the training set and the test set. The model can partly recognize a client's own site patterns rather than learning a signal that generalizes — inflating the score without the model actually improving.

Once client leakage is closed, the honest number is 0.560 — a real 24% drop from the inflated figure. That's the number this report stands behind.

The baseline wins, and that's the honest finding. Error analysis on the model shows why: its top false-positive pattern is pages with expected-low CTR at extreme positions (very strong or very weak) — cases the baseline correctly treats as normal (because it's tier-normalized) but the model, using raw CTR, flags as alarming. The model's added complexity has not yet earned its keep on this feature set.

05 — Limitations

What this cannot claim

  • Observational, not causal. No claim that refreshing a page causes recovery — that requires an actual experiment.
  • One month-pair. March→April 2026 only; not yet validated across seasons or other periods.
  • GSC-only features. GA4 engagement excluded due to ~4% coverage — results say nothing about on-page engagement.
  • Label doesn't rule out consolidation, seasonality, or tracking anomalies. Several flagged pages in manual review looked more like data artifacts (near-zero clicks at strong position) than genuine content problems.
  • Known false-positive pattern. The model over-flags pages with expected-low CTR at extreme positions, since it doesn't tier-normalize CTR the way the baseline does.
  • The baseline currently wins. This report does not claim the model is the better tool for this task, as built.
06 — Ranked recommendations

The action queue, and what a human must check first

Pages are grouped into three reason codes. Every recommendation requires human review before any action — none of this is meant to run unattended.

A
ctr_below_tier_expected → review_metadata_or_snippet

Baseline-driven. CTR sits meaningfully below its position tier's average. Most trustworthy category — directly grounded in the stronger-performing rule.

B
high_decline_risk → priority_content_review

Model-driven. High predicted decline probability. Known to include some false positives at extreme positions — treat with the review checklist below before acting.

C
low_volume_low_confidence → monitor_only

Flagged, but under 200 impressions — real signal is hard to separate from noise at this volume. Watch next cycle rather than act now.

Before acting on any recommendation, a human should check:

  1. Whether a sibling page targeting the same query absorbed the traffic (consolidation), not a real decline.
  2. Whether the drop matches a known seasonal pattern for that topic, rather than a page-specific issue.
  3. For near-zero-click pages at strong position — verify the impression count looks real before treating it as a content problem; it may be a tracking artifact.
Should never be automated
  • Auto-publishing content changes based on score alone.
  • Auto-generating and auto-publishing titles/meta descriptions without human review.
  • Treating a flag as a quality judgment — it's a review priority signal, not proof the page is bad.
  • Any client-facing claim that this system "predicts" or "proves" future performance. It produces observed, directional, decision-support rankings only.

Monitoring / retrain trigger: re-run this pipeline on a fresh month-pair quarterly; if Precision@50 drops more than ~0.10 below this report's 0.52 baseline, treat the ranking as stale and investigate before continued use.
